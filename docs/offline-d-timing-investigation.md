# Variant D: exact source timing and AAC edit/priming

2026-11-15. Research starting point: `e53ead5b7cc51db2829fd2c3944eaee1659344c6`. Production remains `b8ba19af9478e4149f0f86a0088f3779eca6f895`.

## Finding

**D is measurably more faithful to original timing and edit-box representation than A/B/C on the tested fixtures. No improvement in decoded content, native seeking or TikTok rendition quality was demonstrated.** All variants already retain identical encoded HEVC/AAC samples; D additionally retains exact source clocks, sample timing, AAC priming/edit semantics and source duration headers without tolerance or a common timestamp shift.

The previous [A/B report](offline-mp4-ab-investigation.md) identified 60000 → 57600 video-clock quantization. D eliminates that conversion. There is still no evidence connecting these microsecond differences to TikTok's reported 576p result. No new upload tests or personal videos are requested. Nothing is merged into main or deployed.

## Implementation and constraints

The desktop-only [harness](../tools/README.md) now emits `D-source-timing.mp4` alongside A/B/C. D uses A's mdat bytes and existing chunk grouping/physical ordering. It transplants original source:

- Movie header `mvhd`; track headers `tkhd`; media headers `mdhd`, including original clocks and durations.
- Complete `edts`/`elst`, including leading empty edits, media_time/encoder priming offsets, edit durations and rates.
- Raw `stsd` sample entries, plus `stts`, `ctts`, `cslg`, `stss`, `sgpd`, `sbgp` and `sdtp` where present. Missing source boxes remain absent, rather than retaining a replacement generated by A.

Chunk pointers alone are relocated to account for metadata size. D changes no samples, audio rate/pitch/channels, dimensions, orientation, FPS or GOP structure. It adds no AAC tails, silence, tracks, padding, private request flags or fake FPS.

D requires one-to-one original/A sample sizes, counts and ordered packet hashes. The raw stsz sample count must also match FFprobe's represented samples; partially exposed or duplicated edit mappings are rejected. The source must pass existing Smart Copy eligibility. D supports a single normal-rate continuous media edit, optionally preceded by one empty edit. Complex/looped/rate-changing edits, duplicate/unknown sample tables and incompatible layouts fail explicitly. The tool retains header-before-dependent-box ordering: an initial implementation that moved headers after track data yielded no FFprobe packets and was rejected, then corrected before validation passed.

Because it also restores source sample-entry representation and recovery metadata, D is a **source-semantics restoration**, not a single-variable timebase test. For example, MOV may use nclc/progressive-field information whereas A writes nclx. Decoder configuration hashes and decoded HDR color metadata still match. This combined change cannot isolate a particular container field's effect on a hypothetical ingest service.

## Fixtures and independent checks

Five generated MOVs, all rotated 90°, coded 128×72, at source rate 60000/1001 before any explicit VFR selection:

| Fixture | Video | AAC | Coverage |
| --- | --- | --- | --- |
| SDR | 779 frames, approximately 13 seconds, B-frames, keyint 30 | 44.1 kHz mono, 555 packets | Longer timeline; multiple seekable keyframes; delayed audio |
| HLG | 60 frames, 10-bit BT.2020/HLG | 48 kHz stereo, 41 packets | HDR and delayed audio |
| HDR10 | 60 frames, 10-bit BT.2020/PQ, mastering/content-light SEI | 32 kHz stereo, 28 packets | Static HDR metadata and delayed audio |
| Priming | 60 frames, SDR | 48 kHz stereo, 48 packets | Zero input delay, AAC encoder pre-roll/Skip Samples and positive edit media_time |
| VFR | 36 frames, SDR, selected variable cadence, no B-frames | 44.1 kHz mono, 38 packets | Unequal stts durations and delayed audio |

All delayed cases use a 150 ms input audio offset. Actual first AAC presentation time reflects encoder pre-roll and original edit mapping; it is measured, not assumed to be exactly 150 ms. These are synthetic format fixtures, not actual Apple camera captures. Reproduce them with `python3 tools/make-ab-fixtures.py /tmp/NEW_EMPTY_DIRECTORY`.

For every source/output:

1. FFprobe verifies packet count, ordered SHA-256, flags/Skip Samples, exact rational PTS/DTS/duration, codec/extradata, profile, pixel format/depth, color, rate/channels and rotation.
2. Box-level checks require D's source timing/edit/sample-description/recovery boxes to be **byte-identical**. This catches a single AAC edit media_time tick change even if a decoder were to round it away.
3. FFmpeg fully decodes video and audio. Every decoded video frame's pixel hash and ordered frame count match; complete AAC PCM hashes match. PCM comparison alone does not describe presentation gaps, so edits and timestamps are checked separately.
4. FFprobe checks decoded color and mastering/content-light metadata on **every decoded video frame**, supplementing the unchanged encoded packet/configuration hashes.
5. Native accurate input seeks at 20%, 50% and 80% of source video duration compare the decoded video frame and a 100 ms decoded audio window to source. Four outputs × five fixtures × three positions = **60 paired seek comparisons**, all matched. The longer fixture crosses multiple keyframes. Seek points and hashes are in the evidence JSON.

A retains its documented 100 µs source timing tolerance. B/C must retain A's rational packet timing exactly. **D uses zero tolerance and requires zero presentation-origin shift against source**, while preserving original negative decode timestamps and AAC skip semantics. No equal-file-size inference is used.

### AAC edits, priming and A/V synchronization

AAC PTS/DTS/packet-duration errors are **zero for A/B/C/D on all five fixtures**. Original/processed decoded PCM and native seek windows match. Thus these tests found **no audible AAC priming, sample-rate, pitch, channel or synchronization regression in current A**.

In the explicit priming fixture, the source has an AAC edit `(duration=1000 movie ticks, media_time=1024 audio ticks, rate=1)` and FFprobe reports the encoder pre-roll through Skip Samples. A uses `(57600, 1024, 1)` with the 57600 movie clock—semantically equivalent. D preserves `(1000, 1024, 1)` and the original header/group bytes exactly.

The delayed SDR source has an empty edit `(126, -1)` and a media edit `(12888, 0)` at 1000 movie ticks/s. A writes `(7258, -1)` and `(742296, 0)` at 57600 ticks/s. These generated edit-duration values differ slightly from scaling the original rounded durations; D retains the originals. Nevertheless, all AAC packet timestamps and decoded PCM still match in this fixture. Byte-level edit preservation is a real fidelity improvement, not evidence that A's audio was broken.

D preserves the source's complete per-track presentation timelines and relative start/end relationship with zero error. A's video-versus-audio timing deviations are bounded by the small video errors in the tables; the longer test showed no accumulating sample loss/drift. These synthetic checks do not establish perceptual speech lip sync on personal footage.

## Results and next step

**63/63 tests passed, none skipped.** This includes all existing conversion/HDR/audio/UI/cancellation/share regressions plus five expanded offline A/B/C/D fixtures. Negative guards reject changed packet payload/count/configuration, individual timestamp drift, inconsistent stts sample count, rate-changing edits and a one-tick AAC edit mutation. Production build passed and reproduced the committed app bundle unchanged.

The evidence supports this limited conclusion: D is a more exact source-timing/edit remux for eligible, fully represented sample layouts. It does **not** establish a playback/quality improvement: A/B/C/D decode and seek identically on these fixtures. No TikTok processing was invoked. HEVC/AAC payload preservation was already working in A. No HDR enhancement is created, and no Dolby Vision support is added.

**Recommendation: keep D offline and do not deploy.** Next, split D into a timing/header/edit-only restoration and a sample-description/recovery-only restoration to isolate their effects. Expand that offline matrix to additional rational clocks, negative/positive starting offsets, version-1 edit/header boxes, fractional-rate long clips and VFR with B-frame timing ambiguity. The latter currently cannot reach D because A's existing safety check rejects it; general standalone D support would require a separately validated path. A browser-native playback/seek test should follow for those validated outputs, including actual iPhone Safari/Photos HDR behavior, memory and Share Sheet handling. No new TikTok upload round is justified solely by the measurements here.

The branch push uses Cloudflare's documented `[CF-Pages-Skip]` commit prefix so GitHub CI can run without either preview or production deployment. Main stays unchanged. CI result and research commit SHA are reported with delivery.

## Limits

- Native FFmpeg decoding/seeking is **not Safari playback**. Photos HDR appearance, full device playback, touch seeking, resource use and Share Sheet behavior remain untested for D.
- Fixtures are small in resolution and are not authentic iPhone MOVs. The longer clip tests timing/GOP behavior, not 4K/iPhone memory performance.
- Original valid AAC edits are retained rather than generalized, simplified or corrected. Complex edits, multiple descriptions, protected/fragmented inputs and unsupported HDR metadata remain outside this experiment.
- Full decoded pixels and reported HDR metadata matching does not prove perceptual HDR display fidelity on every screen. Dolby Vision remains unsupported.
- The offline implementation buffers files/reports and runs native tools; it is not browser-ready. No server upload, private TikTok flag or compression-bypass claim is introduced.
